Hi Rayson,

Yes you got it. This is a single strong machine I run on unless I need results fast. This is cheaper than going on the cloud if you have the time - I go on the cloud when I need results faster than this machine can give me. I explained this before. Yet if I cannot run 50k+ on a single machine it will be harder on the cloud where there are I/O and NFS issues beyond memory.

1) The machine does not run anything special I know of. It is a fresh install of Ubuntu 12.04, SGE, Anaconda, WxPython, Inspyred, MIST and supporting packages for those. I got the machine only a few days ago - it is almost barebones SGE engine and client.

2) I will play with BerkeleyDB if it will give me a significant advantage in deleting jobs or launching them. My jobs vary in size from tens of minutes to less than a second - about 5k-10k are small jobs the rest are larger. I can endure a couple of hours lost to idle cycles between qmaster schedule intervals if I know this maintains stability and reduces complexity. If a computer is reliable and a bit less efficient it is ok as long as the human does not need to intervene. The issue becomes when the computer becomes less reliable and limits human interaction. So if there is a failure and it takes a couple of hours just to recover from a previous run - just since qdel takes long this is a problem. I rather have things stable then break things while trying to over tune things with my limited understanding. Yet if there is something simple I can do I will try. So far it seems I will try to use on demand scheduling since I can do this through qmon relatively easily.

3) The seg fault that happened a couple of days ago did not report anything special other than a seg fault and core dump in syslog or kern.log. No sign if OOM killer - yet I may not be reading well since this is beyond my experience. It did happen after a couple of days of intensive work with ~70k jobs. This was the first time I tried that many jobs. And at that time I used only 16 slots and used 2 sec scheduling interval. Never the less, to be conservative I restarted with less jobs and more slots and more time between schedules. I will keep this for now in hope this will keep stability. Hopefully nothing will break in this run that should take about week.

Chris, Rayson, you already helped me a lot and gave me a few leads to follow. I guess it is my problem now to figure out my next steps. If I have additional evidence or solutions I can contribute I will report back to the list. Otherwise, thank you both for your help.

          Jacob

>>>> On Mar 30, 2014, at 6:35 AM, Chris Dagdigian <dag_at_bioteam.net> wrote:
>>>>
>>>>
>>>> The #1 suggestion is to change the default scheduling setup over to the
>>>> settings for "on demand scheduling" - you can do that live on a running
>>>> cluster I believe. Google can help you with the parameters but it
>>>> basically involves switching from the looping/cyclical scheduler
>>>> behavior to an event based method where SGE runs a scheduling/dispatch
>>>> cycle each time a job enters or leaves the system. This is purpose built
>>>> for the "many short jobs" use case.
>>>>
>>>> The #2 suggestion is to make sure you use berkeleyDB based spooling
>>>> (this is one scenario where I'll switch from my preference for classic
>>>> spooling) AND make sure that you are spooling to local disk on each node
>>>> instead of spooling back to a shared filesystem. These settings cannot
>>>> easily be changed on a live system so in starcluster land you might have
>>>> to tweak the source code to come up with a different installation
>>>> template that would put these settings in. (Note that I'm not sure what
>>>> SC puts in by default so there is a chance that this is already set up
>>>> the way you'd want ...)
>>>>
>>>> Other stuff:
>>>>
>>>> - SGE Array Jobs are way more efficient than single jobs. Instead of
>>>> 70,000 jobs can you submit a single array job that has *70,000 tasks*
>>>> instead? Or 7 jobs containing 10,000 tasks etc. ?
>>>>
>>>> - Is there any way to batch up or collect your short jobs into bigger
>>>> collections so that the average job run time is longer? SGE is not the
>>>> best at jobs that run for mere seconds or less - most people would batch
>>>> those together to at least get a 60-90 second runtime ...
>>>>
